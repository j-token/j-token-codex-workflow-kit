# 구현 작업 시작하기

확정된 문서를 다시 읽고, 필요한 최소 모델과 추론 강도를 선택한 뒤 별도의 Codex 작업에서 구현을 시작합니다.

## 시작 게이트

다음 조건을 모두 확인합니다.

1. 구현 기준이 되는 문서의 경로와 버전(있으면)이 확인되어야 합니다.
2. 해당 문서를 현재 또는 이전 assistant 응답에서 사용자에게 제시한 뒤, 그 응답을 끝냈어야 합니다.
3. 문서 제시가 끝난 뒤의 별도 사용자 메시지에서, 사용자가 그 문서의 구현·수정·디버깅 시작을 명시적으로 승인해야 합니다.
4. 문서에 반영되지 않은 사용자 피드백이나 구현을 막는 사용자 결정 사항이 없어야 합니다.

승인으로 인정하는 표현은 문서 경로 또는 버전을 다시 확인한 `승인`, `이 문서대로 구현 시작`, `이 버전으로 수정 시작`처럼 명시적인 후속 응답입니다. 최초 요청의 `작성 후 구현해줘`, `먼저 문서화하고 수정해줘`처럼 문서 작성과 구현 의사를 한 문장에 둔 표현은 구현 의사로만 기록하며 승인으로 인정하지 않습니다. 조건을 충족하지 못하면 새 작업을 만들지 않습니다. 모델의 성능을 미확정 요구사항의 대체재로 사용하지 않습니다.

## 문서 제시와 승인 대기

문서 작성 스킬은 문서를 사용자에게 제시한 뒤 다음처럼 승인 대상 경로를 다시 확인하고 현재 턴을 종료합니다.

```text
문서: <문서 경로> (<버전 또는 상태>)
이 문서대로 구현을 시작하려면 다음 메시지에서 `승인` 또는 `이 문서대로 구현 시작`이라고 알려주세요.
```

그 응답 뒤에는 코드 수정, 새 thread 생성, 후속 구현 계획을 진행하지 않습니다. 별도 사용자 메시지가 오면 승인 대상이 제시한 문서와 일치하는지 먼저 확인합니다.

## 문서 재확인

새 작업을 만들기 직전에 구현 문서를 파일에서 한 번 다시 읽습니다. 이전 대화의 요약이나 기억만으로 선택하지 않습니다.

다음 항목을 추출합니다.

- 변경 범위와 예상 파일/모듈 수
- 요구사항의 명확성과 남은 설계 판단
- 외부 시스템, 도구, 플랫폼의 수
- 검증 단계와 실패 재현 난이도
- 보안, 데이터 손실, 배포, 호환성 같은 실패 비용
- 서로 독립적으로 나눌 수 있는 작업의 존재

## 모델 선택

사용자가 모델을 지정하지 않았을 때는 아래 세 모델만 사용합니다.

| 모델 | 선택 기준 |
|---|---|
| `gpt-5.6-luna` | 완료 조건이 명확한 좁고 반복 가능한 변경. 국소 수정, 정형 변환, 단순 테스트 보강처럼 판단 부담과 실패 비용이 낮은 작업 |
| `gpt-5.6-terra` | 기본 선택. 요구사항은 확정되어 있지만 여러 파일, 도구 사용, 일반적인 디버깅과 검증이 필요한 일상적 구현 |
| `gpt-5.6-sol` | 복잡하고 개방적인 고가치 작업. 아키텍처 판단, 여러 시스템·플랫폼의 상호작용, 어려운 원인 분석, 보안·데이터·호환성 위험처럼 깊은 판단과 높은 완성도가 필요한 구현 |

경계에 걸리면 다음 순서로 판단합니다.

1. 완료 조건이 명확하고 절차가 반복 가능하면 Luna를 선택합니다.
2. 문서가 충분히 구체적이고 일반적인 다중 파일 구현이면 Terra를 선택합니다.
3. 구현 중 중요한 판단이 남거나 실패 비용이 크면 Sol을 선택합니다.
4. 단순히 작업량이 많다는 이유만으로 Sol을 선택하지 않습니다.

## 추론 강도 선택

필요한 결과를 낼 수 있는 가장 낮은 강도를 선택합니다.

| 강도 | 선택 기준 |
|---|---|
| `low` | 짧고 국소적이며 구현 경로와 검증 방법이 모두 명확함 |
| `medium` | 기본 선택. 몇 단계의 계획, 코드 탐색, 테스트가 필요한 일반 구현 |
| `high` | 여러 모듈·도구·검증 단계 또는 의미 있는 트레이드오프가 있음 |
| `xhigh` | 복잡한 아키텍처, 어려운 디버깅, 고위험 변경처럼 깊은 분석과 재검증이 필요함 |
| `max` | 단일 작업으로 풀어야 하는 가장 어려운 문제이며 속도와 사용량보다 깊이가 중요함 |
| `ultra` | 자동 선택하지 않음. 사용자가 명시적으로 요청하고 작업을 독립된 하위 작업으로 나눌 수 있을 때만 사용함 |

대부분의 작업은 `medium` 이하에서 시작합니다. 파일 수만으로 강도를 높이지 말고, 판단의 수·상호작용·실패 비용을 기준으로 높입니다.

## 사용자 지정 우선

- 사용자가 모델을 지정하면 세 기본 모델 밖의 모델이어도 그대로 따릅니다.
- 사용자가 추론 강도를 지정하면 그대로 따릅니다.
- 현재 새 작업 생성 기능이 해당 모델과 강도의 조합을 지원하는지 도구 스키마에서 확인합니다.
- 지원되지 않는 조합이면 임의로 바꾸지 말고, 지원되지 않는 항목과 가능한 조합을 알려 확인받습니다.
- 사용자가 속도를 별도 인자로 지정하지 않았다면 `speed`나 `service_tier`를 만들지 않습니다. 새 작업의 속도는 모델과 추론 강도로만 간접 조절합니다.

## 새 작업 생성

이 절차는 현재 호스트가 모델에 `thread/start`와 `turn/start`를 호출할 수 있는 도구 표면을 제공할 때만 적용합니다. 로컬 App Server에 이 API가 있더라도 현재 모델에 도구로 노출되지 않았다면 사용할 수 있는 것으로 간주하지 않습니다.

1. 사용자에게 선택 결과와 근거를 한 문장으로 알립니다.
2. `thread/start`를 호출해 새 thread를 만듭니다. 인자에는 선택한 `model`과 현재 프로젝트의 절대 `cwd`를 넣습니다.
3. 반환된 `threadId`로 `turn/start`를 호출합니다. `effort`에 선택한 추론 강도를 넣고, `input`에는 아래 텍스트 하나만 넣습니다.

```text
아래의 문서를 읽으세요
- <문서 경로>
```

문서가 여러 개면 같은 목록에 경로를 한 줄씩 추가합니다. 전달 프롬프트에는 구현 방식, 작업 트리, 범위, 검증, 결과 보고 지시를 덧붙이지 않습니다. 새 thread와 첫 turn 생성에 성공하면 현재 작업에서는 구현을 계속하지 않습니다.

## 실패 처리

- `thread/start` 또는 `turn/start`가 현재 모델 도구로 노출되지 않았으면 현재 작업에서 대신 구현하지 않습니다. 지원되지 않는 도구 표면임을 보고합니다.
- 선택한 모델, 추론 강도, 전달할 프롬프트를 사용자에게 제공하고 새 작업을 만들 수 없었던 이유를 설명합니다.
- 프로젝트를 찾지 못하거나 문서 경로를 새 작업에서 읽을 수 없으면 먼저 그 문제를 해결합니다.

## 동작 확인 시나리오

다음 시나리오로 문서 작성 스킬의 종료 응답과 이 스킬의 시작 게이트를 확인합니다.

| 시나리오 | 기대 결과 |
|---|---|
| 사용자가 `문서 작성 후 구현해줘`라고 최초 요청 | 문서를 작성·제시하고 승인 안내를 남긴 뒤 현재 턴을 끝낸다. 코드 수정과 새 thread 생성은 하지 않는다. |
| 문서 제시 뒤 사용자가 `승인`이라고 응답 | 제시한 문서가 하나로 식별되면 새 thread 생성 절차를 시작한다. 식별되지 않으면 문서 경로 또는 버전을 확인한다. |
| 문서 제시 뒤 사용자가 다른 문서의 구현을 요청 | 승인 대상이 다르므로 해당 문서를 제시·확정하는 흐름으로 돌아간다. 기존 문서를 승인으로 재사용하지 않는다. |
| 호스트에 `thread/start` 또는 `turn/start` 도구가 없음 | 현재 작업에서 구현하지 않고 지원되지 않는 도구 표면과 선택한 설정·최소 전달 프롬프트를 보고한다. |
| 두 문서를 함께 승인 | `turn/start.input`은 `아래의 문서를 읽으세요` 뒤에 두 경로만 나열하며, 다른 구현 지시는 포함하지 않는다. |

## 선택 예시

- 단일 컴포넌트의 명확한 문구와 테스트 수정: `gpt-5.6-luna` + `low`
- 확정된 스펙에 따른 일반적인 다중 파일 기능 구현: `gpt-5.6-terra` + `medium`
- 여러 플랫폼의 상태·보안 경계를 바꾸는 런타임 구현: `gpt-5.6-sol` + `high` 또는 `xhigh`
