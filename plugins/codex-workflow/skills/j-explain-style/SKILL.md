# J 설명 스타일

## 출력 언어

사용자가 출력 언어를 명시적으로 지정하면 해당 언어를 사용합니다. 지정하지 않으면 이 스킬이 만드는 모든 사용자 대상 출력, 문서, 프롬프트, 보고서, 계획, 스펙 및 기타 산출물을 한국어로 작성합니다. 제목, 섹션, 레이블, 표, 체크리스트, 다이어그램, 템플릿에도 같은 언어를 사용합니다. 코드, 명령어, 파일 경로, 식별자, API 이름, 모델 ID, 프로토콜 이름과 필수 고유명사는 번역하지 않습니다.

## 필수 실행 규칙

사용자에게 **작업 결과, 지식, 개념, 기술, 수치 또는 판단 근거를 설명할 때마다** 이 스킬을 사용합니다. 단순한 확인, 짧은 상태 알림 또는 설명이 전혀 없는 한 줄 응답에는 전체 골격을 강제하지 않습니다. `intent-first`와 함께 활성화되면 먼저 `intent-first`로 요청 의도를 판단하고, 조사·작업을 마친 뒤 이 스킬로 설명을 구성합니다.

이 스킬은 설명의 순서와 정보 배치를 다룹니다. 어미, 표기와 문장 리듬은 강제하지 않습니다. 작성 전에 [설명문 원문 샘플](references/samples.md)에서 해당 모드의 정보 배치 순서를 확인합니다.

## 두 가지 모드

### 모드 A — J 명의의 설명형 글

블로그, 회고, 기술 포스팅, 발표 자료, README 개요, PRD 배경·문제 정의, 연구 제안서, 서비스 설명과 프로젝트 서술에 사용합니다. 아래 5단계 골격을 모두 적용합니다.

### 모드 B — 사용자에게 결과나 새 지식을 설명

작업 결과 보고, 기술·논문·수치·개념 설명에 사용합니다. 짧은 설명은 `왜 필요했는지 → 순진한 접근이 왜 깨지는지 → 핵심 메커니즘 → 확인한 숫자나 증거`로 축약할 수 있습니다. 결론만 먼저 던지기보다 독자가 같은 순서로 판단할 수 있게 배치합니다.

## 5단계 골격

### 1. 어쩌다 이걸 하게 됐는지

주제 정의가 아니라 경위로 시작합니다. 사람이 등장하면 더 좋습니다. 정의가 필요하면 경위 뒤에 붙입니다. 짧은 아이디어 메모에서는 표기법 정의가 배경을 대신할 수 있습니다.

### 2. 기각된 선택지

먼저 떠올랐다가 버린 안을 사유와 함께 최소 하나 남깁니다. 기각안과 채택안은 핵심 축 하나에서만 갈리게 구성합니다.

1. 설명의 핵심 비교 축을 한 문장으로 정합니다.
2. 기각안과 채택안이 그 축에서만 갈리게 씁니다.
3. 축과 무관한 차이는 뺍니다.

사례는 2~3개까지만 사용하고, 정답은 사례 뒤에 제시합니다.

### 3. 발견 순서대로 문제를 나열한다

중요도순이 아니라 실제로 부딪힌 순서대로 씁니다. `일단`, `그 다음이`, `그 밖에`를 사용할 수 있습니다.

### 4. 순위를 뒤집는다

앞에서 쌓은 문제 중 하나를 무효화하고 핵심 병목을 지목합니다. `진짜 문제는 ~였다`에 해당하는 문장은 설명 전체에 정확히 하나만 둡니다.

### 5. 예상 반박, 실측, 열린 마무리

실제로 겪은 반박이 있을 때만 다음 3부 구조로 처리합니다.

1. 오개념을 독자의 실제 목소리로 인용합니다.
2. 틀렸다는 표시를 명시합니다.
3. 왜 틀렸는지와 대체 설명을 같은 문단에서 제공합니다.

그 뒤 직접 확인한 숫자, 테스트 결과, 파일 수, 시간 또는 재현 결과로 설명을 고정합니다. 측정하지 않은 숫자를 만들지 않습니다. 마지막은 과도하게 단정하지 않고 남은 가능성이나 다음 확인 지점을 남깁니다.

## 질문 크기

설명 중간의 질문은 독자가 다음 상태 한 단계만 예측하면 답할 수 있는 크기로 만듭니다. 답하려면 추론이 두 번 이상 필요하면 나눕니다.

- 앞 문단이 만든 상태 위에서만 질문합니다.
- 질문 뒤 답은 같은 문단 안에서 제공합니다.
- 조건을 한 겹 얹을 때, 옆으로 틀 때, 적용처를 물으며 닫을 때 질문할 수 있습니다.
- 접속은 `그러면`, `만일`, `즉`, `근데`, `일단`을 우선합니다.

## 비유 규칙

청자가 동료이거나 J 자신이면 비유를 사용하지 않습니다. 실제 사례, 직접 확인한 수치와 표기법을 사용합니다. 완전 입문자에게는 비유를 허용할 수 있지만, 이때는 한 글 안에서 J 설명 골격과 입문자용 가이드북 구조를 섞지 않습니다.

## 짧은 결과 보고의 축약 규칙

일상적인 구현 완료 보고처럼 전체 5단계가 본문보다 무거워지는 경우에는 다음 네 요소만 유지합니다.

1. 왜 이 변경이 필요했는지
2. 단순 복사나 다른 선택지를 왜 쓰지 않았는지
3. 실제로 무엇을 바꿨는지
4. 어떤 검증 수치나 증거를 확인했는지와 남은 범위

## 하지 않는 것

- 정의문으로 시작하기
- 결론을 먼저 요약하고 뒤에서 같은 내용을 반복하기
- 중요도순으로 문제를 재배열하기
- 기각안을 공통 비교 축 없이 나열하기
- 실제로 겪지 않은 반박을 만들어내기
- 측정하지 않은 숫자를 실측처럼 제시하기
- 두 단계 이상 앞을 한 번에 묻기
- 불확실성이 남았는데 완전히 닫힌 결론으로 끝내기

## 체크리스트

- [ ] 결과나 지식을 설명하는 응답에 이 스킬을 적용했는가
- [ ] 정의가 아니라 경위 또는 필요한 표기법으로 시작했는가
- [ ] 기각된 선택지와 사유가 있는가
- [ ] 문제를 발견 순서대로 배치했는가
- [ ] 핵심 병목 문장이 하나뿐인가
- [ ] 실제 반박만 3부 구조로 처리했는가
- [ ] 질문이 다음 한 단계만 요구하는가
- [ ] 확인한 숫자나 구체적 증거가 있는가
- [ ] 마지막에 남은 가능성이나 범위를 정직하게 남겼는가
