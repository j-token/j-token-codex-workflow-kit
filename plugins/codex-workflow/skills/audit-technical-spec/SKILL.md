# 기술 스펙 독립 감사

## 출력 언어

사용자가 출력 언어를 명시적으로 지정하면 해당 언어를 사용합니다. 지정하지 않으면 이 스킬이 만드는 모든 사용자 대상 출력, 문서, 프롬프트, 보고서, 계획, 스펙 및 기타 산출물을 한국어로 작성합니다. 제목, 섹션, 레이블, 표, 체크리스트, 다이어그램, 템플릿에도 같은 언어를 사용합니다. 코드, 명령어, 파일 경로, 식별자, API 이름, 모델 ID, 프로토콜 이름과 필수 고유명사는 번역하지 않습니다.

## 작성 문서 첨부

요청된 모든 문서의 작성 또는 갱신을 마친 뒤 최종 응답에 각 문서를 `[문서 이름](절대 경로)` 형식의 Markdown 링크로 반드시 첨부합니다. 링크에는 독립된 디렉터리 세그먼트로 구성된 절대 경로를 사용하고, 디렉터리 구분자를 생략하거나 경로 세그먼트를 붙여 쓰지 않습니다. Windows 경로를 문자열로 표시할 때는 `C:\\Users\\WinUser\\Documents\\폴더\\문서.md`처럼 각 역슬래시를 두 번 씁니다.

## SHA-256 표기

- 파일 동일성 검증에는 전체 SHA-256을 계산하고 내부적으로 비교합니다.
- 사용자 대상 응답, 감사 보고서, 표와 인계 설명에는 전체 값을 쓰지 않고 대문자 기준 `앞 4자리…뒤 4자리` 형식만 표시합니다. 예: `ABCD…1234`.
- 축약 표시는 가독성을 위한 fingerprint이며, 실제 비교를 축약 문자열 비교로 대체하지 않습니다.
- 하위 감사 에이전트 입력에는 전체 SHA-256을 전달할 수 있지만 결과 보고서와 사용자 응답에는 축약형만 기록하게 합니다.

## 목적

기술 스펙 작성자와 분리되고 대화 컨텍스트를 상속하지 않은 하위 에이전트가 스펙의 주장과 구현 계획을 실제 소스 오브 트루스에 대조하게 합니다. 감사는 문장 품질이나 발견 0건을 목표로 하지 않고 다음 질문에 근거로 답하는 구현 전 게이트입니다.

- 현재 저장소 구조와 계약으로 스펙대로 구현할 수 있는가?
- 구현 전에 해결해야 할 블로커나 사용자 결정이 남아 있는가?
- 파일, 모듈, 타입, API, 설정, 버전, 플랫폼 동작을 실제와 다르게 적은 곳이 있는가?
- 테스트, 마이그레이션, 보안, 호환성과 롤백 계약이 구현을 검증하기에 충분한가?

감사의 목표는 불확실성을 모두 없애는 것이 아니라 구현을 안전하게 시작할 수 있는 최소 충분 계약을 확인하는 것입니다. 구현으로 검증할 수 있는 내부 선택은 스펙을 확장하지 않고 코드, 설정, 테스트, spike 또는 ADR로 이관합니다.

## 스펙과 구현의 책임 경계

다음 항목은 구현 전에 스펙에서 확정하거나 명시적인 블로커로 남깁니다.

- PRD 핵심 요구사항과 수용 기준
- 공개 API, 프로토콜, 영속 데이터와 교차 모듈 경계
- 데이터 누출, 보안, 개인정보, 호환성, migration과 rollback 경계
- 평가·승격 기준, 모델 입력·출력, 합법 행동과 재현성 계약
- 여러 구현자가 다르게 해석하면 상호 운용이나 사용자 결과가 달라지는 결정

다음 항목은 별도 근거가 없으면 기술 스펙 수정 사유로 삼지 않고 구현 단계로 이관합니다.

- 단일 모듈 내부 자료구조, private 함수와 지역 변수 이름
- 중간 artifact의 세부 필드와 파일명, 내부 상태 이름
- 외부 동작에 영향을 주지 않는 deterministic tie-break와 정렬 순서
- 테스트나 짧은 spike로 안전하게 확정할 수 있는 기본값과 최적화
- 아직 생성되지 않은 산출물의 전체 schema, SHA 소유 순서와 내부 DAG 표현

후자의 항목이 실제로 공개 계약, 데이터·보안, 통계적 타당성, 재현성 또는 수용 기준에 영향을 준다는 근거가 있을 때만 전자로 승격합니다.

## 감사 시작 게이트

다음 조건을 모두 확인합니다.

1. 감사할 기술 스펙의 절대 경로와 문서 버전이 확인되어야 합니다.
2. 스펙 파일을 현재 저장소에서 읽을 수 있어야 합니다. 채팅 본문만 있는 스펙은 먼저 파일로 저장합니다.
3. 저장소의 절대 `cwd`를 확인해야 합니다.
4. 감사 보고서 경로를 미리 정해야 합니다. 사용자가 지정하지 않으면 스펙 파일과 같은 `.codex/temp/` 또는 저장소 루트의 `.codex/temp/`에 `<스펙 stem>-audit.md`로 정합니다.
5. 같은 스펙 버전과 SHA-256에 대한 미해결 감사 에이전트가 이미 있으면 중복으로 시작하지 않습니다.

기술 스펙 작성 직후의 독립 감사는 읽기·조사와 감사 보고서 작성만 수행하므로 별도 구현 승인을 요구하지 않습니다. 사용자가 감사를 명시적으로 제외해도 제품·기능 기술 스펙의 구현 게이트는 충족되지 않은 상태로 남습니다.

## 독립성 및 변경 제한

- 감사 에이전트는 `fork_turns: "none"`으로 생성하여 현재 대화 컨텍스트를 상속하지 않게 합니다.
- 감사 에이전트에는 작성자의 결론, 의도한 답, 예상 발견 사항을 전달하지 않습니다. 저장소, PRD, 기술 스펙, 해시와 보고서 경로처럼 감사에 필요한 원본만 전달합니다.
- 감사 에이전트는 제품 코드, 테스트, 설정, 기술 스펙을 수정하지 않습니다.
- 감사 에이전트가 쓸 수 있는 파일은 지정한 감사 보고서 하나뿐입니다.
- 블로커를 직접 해결하거나 스펙을 조용히 보정하지 않고 근거와 권고 수정안을 보고합니다.
- 감사 에이전트는 다른 구현 작업을 시작하거나 하위 작업으로 재인계하지 않습니다.

## 조사 범위와 재감사 범위

최초 감사에서는 스펙의 중요한 주장을 추적 가능한 단위로 대조합니다.

1. 승인된 PRD와 요구사항 추적표를 대조합니다.
2. 저장소의 실제 진입점, 모듈, 타입, 공개 API, 데이터 모델, 설정, 빌드·배포 경로와 테스트를 확인합니다.
3. 스펙에 적힌 파일 경로, 식별자, 명령어와 버전이 실제로 존재하거나 계획된 신규 항목으로 명확히 구분됐는지 확인합니다.
4. 상태 전이, ownership, threading, lifecycle, 오류 처리, 보안 경계, 호환성, migration과 rollback이 구현 가능한 계약인지 확인합니다.
5. 외부 API, SDK, 플랫폼 또는 프로토콜에 의존하는 주장은 해당 공식 문서나 저장소의 고정된 버전 자료를 대조합니다. 최신성에 민감한 정보는 반드시 현재 공식 자료로 검증합니다.
6. 테스트 스펙이 핵심 요구사항, 실패 모드와 블로커 해소를 검증할 수 있는지 확인합니다.
7. 구현 순서의 순환 의존성, 사용할 수 없는 도구·권한·자격 증명, 미정 데이터 마이그레이션과 배포 전제 조건을 찾습니다.

문서에 없는 새 제품 범위를 제안하는 일반 리뷰는 하지 않습니다. 각 발견은 구현 가능성이나 정확성에 직접 영향을 주어야 합니다.

재감사는 수정된 계약과 그 직접 영향 범위만 확인합니다. 아키텍처·공개 API·데이터 모델·보안 경계처럼 기반 계약이 바뀐 경우에만 전체 감사를 다시 수행합니다. 표현 정리, 구현 TODO 추가, private 세부사항 변경 때문에 전체 문서를 재감사하지 않습니다.

## 발견 사항 분류

각 발견에 `AUD-001`부터 순번을 부여하고 다음 필드를 기록합니다.

| 필드 | 내용 |
|---|---|
| 심각도 | `블로커`, `중요`, `경미` |
| 유형 | `사실 불일치`, `구현 불가능`, `계약 누락`, `검증 공백`, `외부 의존성`, `요구사항 불일치` |
| 스펙 근거 | 섹션, 표, 계약 또는 라인 |
| 실제 근거 | 저장소 `path:line`, 실행 결과 또는 공식 자료 |
| 영향 | 그대로 구현할 때 실패하거나 달라지는 동작 |
| 권고 | 스펙 수정, 사용자 결정 또는 선행 작업 |
| 처리 위치 | `스펙`, `구현 TODO`, `테스트`, `ADR`, `spike` 중 하나 |

심각도는 다음 기준을 사용합니다.

- `블로커`: 현재 정보나 구조로 구현을 시작할 수 없거나, 시작하면 핵심 요구사항·데이터·보안·호환성을 위반합니다.
- `중요`: 구현은 가능하지만 실제 동작·수용 기준·재현성 또는 교차 모듈 계약을 신뢰하기 어려워 구현 중 명시적으로 처리해야 합니다. 중요 발견 자체는 구현 시작을 막지 않습니다.
- `경미`: 구현과 핵심 검증을 막지 않는 정합성 또는 명료성 문제입니다.

구현자가 안전하게 결정할 수 있는 세부사항을 `블로커`나 `중요`로 올리지 않습니다. 구현 시작이 정말 불가능하거나 핵심 요구사항·데이터·보안·호환성을 위반하는 경우만 `블로커`로 분류합니다.

## 판정

감사 보고서의 판정은 하나만 사용합니다.

- `통과`: 블로커가 없고 중요 발견이 구현 TODO·테스트·ADR·spike 중 하나로 배치되어 구현을 시작할 수 있습니다.
- `조건부 통과`: 블로커는 없지만 영향을 받는 구현 영역에 들어가기 전에 사용자 결정이나 외부 입력이 필요한 중요 발견이 있습니다. 영향받지 않는 구현은 시작할 수 있습니다.
- `차단`: 블로커가 하나 이상 있습니다.

발견 0건이나 중요 발견 0건을 통과 조건으로 삼지 않습니다. `조건부 통과`는 전체 구현을 멈추는 판정이 아니라 해당 결정에 의존하는 영역만 보류하는 판정입니다. 중요 발견을 닫기 위해 private 구현 세부사항을 기술 스펙에 계속 추가하지 않습니다.

## 감사 보고서 구조

```md
# 기술 스펙 감사 보고서: <대상>

**감사 판정:** 통과 | 조건부 통과 | 차단
**감사한 스펙:** <절대 경로>
**스펙 버전:** <버전>
**스펙 SHA-256:** <앞4…뒤4>
**승인된 PRD:** <절대 경로 또는 없음>
**PRD 버전:** <버전 또는 없음>
**PRD SHA-256:** <앞4…뒤4 또는 없음>
**저장소:** <절대 cwd>
**감사 시각:** <ISO 8601>

## 요약

## 구현 가능성

## 블로커

## 사실 불일치

## 계약 및 검증 공백

## 발견 사항

| ID | 심각도 | 유형 | 스펙 근거 | 실제 근거 | 영향 | 권고 | 처리 위치 |
|---|---|---|---|---|---|---|---|

## 확인한 근거

## 구현 전 필수 조치

## 감사 범위와 한계
```

발견이 없는 섹션에는 `없음`이라고 명시합니다. 실행하지 못한 검증과 접근하지 못한 외부 자료는 성공한 것처럼 쓰지 않고 `감사 범위와 한계`에 기록합니다.

## 모델과 추론 강도

사용자가 지정하지 않으면 기본값으로 `gpt-5.6-sol`과 `high`를 사용합니다. 감사 대상이 좁고 로컬 저장소만 대조하면 `gpt-5.6-terra`와 `medium`을 사용할 수 있습니다. 여러 플랫폼, 외부 계약, 보안·데이터·호환성 위험 또는 상충하는 자료가 있으면 `gpt-5.6-sol`과 `xhigh`를 사용합니다.

사용자가 모델이나 추론 강도를 지정하면 우선하되, 현재 하위 에이전트 생성 도구가 해당 조합을 지원하지 않으면 가능한 조합을 알려 확인받습니다.

## 무컨텍스트 감사 에이전트 생성

현재 호스트가 `spawn_agent`를 제공할 때만 감사 에이전트를 만듭니다. 이 감사는 일반적인 선택적 위임이 아니라 기술 스펙 작성 직후의 필수 독립 검증 체크포인트입니다.

1. 현재 기술 스펙과 같은 주제를 나타내는 감사 작업 이름을 짓습니다.
2. 선택한 모델, 추론 강도와 감사 보고서 경로를 사용자에게 알립니다.
3. 기술 스펙 파일과 승인된 PRD 파일의 SHA-256을 계산합니다. PRD가 없으면 PRD 경로, 버전과 SHA-256을 모두 `없음`으로 둡니다.
4. `spawn_agent`를 `fork_turns: "none"`으로 호출합니다. 지원되는 경우 선택한 모델과 추론 강도를 전달합니다.
5. 에이전트에게 다음 입력 전체를 전달합니다.

```text
# 지시 사항

## 목표

첨부한 기술 스펙을 실제 저장소, 승인된 요구사항과 필요한 공식 자료에 독립적으로 대조하여 구현 가능성, 블로커, 사실 불일치, 누락된 계약과 검증 공백을 조사하세요.

## 해야할것

- 기술 스펙 전체를 읽고 중요한 주장을 추적하세요.
- 저장소의 실제 코드, 설정, 빌드·배포 경로와 테스트를 근거 라인까지 확인하세요.
- 외부 계약에 의존하는 주장은 공식 자료로 확인하세요.
- 각 발견을 `AUD-*` ID, 심각도, 유형, 근거, 영향과 권고로 기록하세요.
- 각 발견이 스펙 수정 대상인지, 구현 TODO·테스트·ADR·spike로 이관할 항목인지 구분하세요.
- 단일 모듈 내부 결정이나 구현으로 검증할 세부사항을 스펙 누락으로 확대하지 마세요.
- `통과`, `조건부 통과`, `차단` 중 하나로 판정하세요.
- 감사한 스펙과 승인된 PRD의 전체 SHA-256이 아래 값과 일치하는지 내부적으로 확인하고, 보고서에는 `앞4…뒤4`만 표시하세요.
- 지정한 경로에 사용자가 지정한 언어로 감사 보고서를 작성하고, 지정하지 않았다면 한국어로 작성한 뒤 최종 응답에 링크를 첨부하세요.
- 수정 허용 파일: <감사 보고서의 저장소 상대 경로>

## 하면 안될 것

- 제품 코드, 테스트, 설정 또는 기술 스펙을 수정하지 마세요.
- 근거 없이 구현 가능하다고 추정하지 마세요.
- 문장 취향이나 새 제품 아이디어를 감사 발견으로 확대하지 마세요.
- 발견 0건을 만들기 위해 private 구현 세부사항, 미래 artifact schema 또는 명백한 tie-break를 스펙에 추가하도록 요구하지 마세요.
- 구현을 시작하거나 다른 작업으로 재인계하지 마세요.
- 수정 금지 파일: 감사 보고서 외 모든 파일

## 유의사항

- 판정 기준:
  - `통과`: 블로커가 없고 중요 발견의 처리 위치가 구현 TODO·테스트·ADR·spike로 정해짐
  - `조건부 통과`: 블로커는 없지만 특정 구현 영역 전에 사용자 결정이나 외부 입력이 필요함
  - `차단`: 블로커가 하나 이상 있음
- 입력:
  - 저장소: <절대 cwd>
  - 기술 스펙: <절대 경로>
  - 스펙 버전: <버전>
  - 스펙 SHA-256: <해시>
  - 승인된 PRD: <절대 경로 또는 없음>
  - PRD 버전: <버전 또는 없음>
  - PRD SHA-256: <해시 또는 없음>
  - 감사 보고서: <절대 경로>
- 검증 기준: 보고서의 스펙 경로·버전·SHA-256, 승인된 PRD 경로·버전·SHA-256, 판정과 근거가 모두 채워져야 합니다.
- 파일 소유권: 단일 작성자, 감사 보고서만 수정할 수 있습니다.
- 결과 보고: 판정, 발견 사항 수, 보고서 경로와 확인하지 못한 범위를 요약하세요.
```

6. 감사 에이전트가 끝날 때까지 기다립니다.
7. 루트 에이전트가 보고서 존재 여부, 허용 파일 밖 변경, 대상 경로, 버전, SHA-256, 승인된 PRD 경로·버전·SHA-256, 판정과 근거를 직접 검증합니다.
8. `차단`이면 블로커에 필요한 최소 계약만 스펙에 반영하고 변경된 계약과 직접 영향 범위만 새 무컨텍스트 감사 에이전트로 재감사합니다. `조건부 통과`나 `통과`의 비차단 발견은 구현 TODO·테스트·ADR·spike로 이관하고 전체 재감사를 반복하지 않습니다.
9. 같은 종류의 비차단 발견이 두 감사에서 반복되면 더 자세한 스펙을 작성하지 말고 구현 단계 검증 항목으로 고정합니다.

## 실패 처리

- `spawn_agent`가 현재 모델의 도구로 노출되지 않았으면 현재 에이전트가 감사를 대신 수행하지 않습니다.
- 가용 슬롯이 부족하면 실행 중인 관련 에이전트가 끝날 때까지 기다린 뒤 생성을 다시 시도합니다.
- 생성 호출 오류, 감사 에이전트의 중단·무응답 또는 대기 실패가 발생하면 동일한 원본 입력과 `fork_turns: "none"`으로 한 번만 재시도합니다.
- 재시도도 실패하면 루트 에이전트가 감사를 대신 수행하지 않으며 구현 게이트를 미충족 상태로 유지합니다.
- 선택한 모델, 추론 강도, 감사 에이전트를 만들 수 없는 이유와 전달하려던 정확한 전체 프롬프트를 사용자에게 제공합니다.
- 보고서가 생성되지 않았거나 판정, 스펙 버전, 축약 SHA-256, 승인된 PRD 경로·버전·축약 SHA-256 중 하나가 없으면 감사가 완료된 것으로 보지 않습니다. PRD가 없는 작업은 세 PRD 필드에 `없음`을 명시해야 합니다.
- 감사 에이전트가 보고서 외 파일을 변경했다면 해당 변경을 감사 결과로 신뢰하지 않고 사용자에게 알립니다.

## 구현 인계 조건

`start-implementation-thread`로 넘기기 전에 다음을 확인합니다.

- 감사 보고서의 스펙 경로, 버전과 축약 SHA-256이 현재 기술 스펙과 일치하며, 현재 파일의 전체 SHA-256을 내부적으로 다시 계산했습니다.
- 감사 보고서의 승인된 PRD 경로, 버전과 축약 SHA-256이 기술 스펙이 참조하는 승인된 PRD와 일치하며, 현재 파일의 전체 SHA-256을 내부적으로 다시 계산했습니다.
- 감사 이후 PRD가 바뀌었다면 기술 스펙과의 정합성을 다시 확인하고 변경된 핵심 계약과 직접 영향 범위를 새 PRD·스펙 SHA-256으로 재감사했습니다.
- 판정이 `통과` 또는 `조건부 통과`이고 블로커가 없습니다.
- 중요 발견은 구현 TODO·테스트·ADR·spike 또는 영향을 받는 영역의 보류 조건으로 배치됐습니다.
- 감사 이후 핵심 계약이 바뀌었다면 변경된 계약과 직접 영향 범위를 새 SHA-256으로 재감사했습니다.

하나라도 충족하지 못하면 구현 승인을 받아도 새 구현 thread를 만들지 않습니다.

## 동작 확인 시나리오

| 시나리오 | 기대 결과 |
|---|---|
| 기술 스펙 파일 작성 완료 | 별도 승인 없이 `fork_turns: "none"`인 감사 에이전트를 생성하고 현재 에이전트는 구현하지 않습니다. |
| 감사 판정이 `차단` | 블로커를 기술 스펙에 반영한 뒤 재감사합니다. |
| 감사 판정이 `조건부 통과` | 중요 발견을 구현 TODO·테스트·ADR·spike 또는 영향 영역 보류 조건으로 배치하고 전체 구현을 불필요하게 멈추지 않습니다. |
| 감사 뒤 핵심 계약 변경 | 기존 보고서를 재사용하지 않고 변경된 계약과 직접 영향 범위를 새 SHA-256으로 재감사합니다. |
| 감사 판정이 `통과` 또는 `조건부 통과`이고 블로커가 없음 | 사용자 승인 뒤 `start-implementation-thread`의 나머지 게이트를 확인합니다. |
| `spawn_agent` 도구가 없음 | 정확한 감사 프롬프트를 제공하고 구현 게이트를 미완료 상태로 둡니다. |
