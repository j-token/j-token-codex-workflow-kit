# 기술 스펙 독립 감사

## 출력 언어

이 스킬이 만드는 모든 사용자 대상 출력, 문서, 프롬프트, 보고서, 계획, 스펙 및 기타 산출물은 한국어로 작성합니다. 제목, 섹션, 레이블, 표, 체크리스트, 다이어그램, 템플릿도 한국어로 작성합니다. 코드, 명령어, 파일 경로, 식별자, API 이름, 모델 ID, 프로토콜 이름과 필수 고유명사는 번역하지 않습니다.

## 작성 문서 첨부

요청된 모든 문서의 작성 또는 갱신을 마친 뒤 최종 응답에 각 문서를 `[문서 이름](절대 경로)` 형식의 Markdown 링크로 반드시 첨부합니다. 링크에는 독립된 디렉터리 세그먼트로 구성된 절대 경로를 사용하고, 디렉터리 구분자를 생략하거나 경로 세그먼트를 붙여 쓰지 않습니다. Windows 경로를 문자열로 표시할 때는 `C:\\Users\\WinUser\\Documents\\폴더\\문서.md`처럼 각 역슬래시를 두 번 씁니다.

## 목적

기술 스펙 작성자와 분리된 새 thread가 스펙의 주장과 구현 계획을 실제 소스 오브 트루스에 대조하게 합니다. 감사는 문장 품질 리뷰가 아니라 다음 질문에 근거로 답하는 구현 전 게이트입니다.

- 현재 저장소 구조와 계약으로 스펙대로 구현할 수 있는가?
- 구현 전에 해결해야 할 블로커나 사용자 결정이 남아 있는가?
- 파일, 모듈, 타입, API, 설정, 버전, 플랫폼 동작을 실제와 다르게 적은 곳이 있는가?
- 테스트, 마이그레이션, 보안, 호환성과 롤백 계약이 구현을 검증하기에 충분한가?

## 감사 시작 게이트

다음 조건을 모두 확인합니다.

1. 감사할 기술 스펙의 절대 경로와 문서 버전이 확인되어야 합니다.
2. 스펙 파일을 현재 저장소에서 읽을 수 있어야 합니다. 채팅 본문만 있는 스펙은 먼저 파일로 저장합니다.
3. 저장소의 절대 `cwd`를 확인해야 합니다.
4. 감사 보고서 경로를 미리 정해야 합니다. 사용자가 지정하지 않으면 스펙 파일과 같은 `.codex/temp/` 또는 저장소 루트의 `.codex/temp/`에 `<스펙 stem>-audit.md`로 정합니다.
5. 같은 스펙 버전과 SHA-256에 대한 미해결 감사 thread가 이미 있으면 중복으로 시작하지 않습니다.

기술 스펙 작성 직후의 독립 감사는 읽기·조사와 감사 보고서 작성만 수행하므로 별도 구현 승인을 요구하지 않습니다. 사용자가 감사를 명시적으로 제외해도 제품·기능 기술 스펙의 구현 게이트는 충족되지 않은 상태로 남습니다.

## 독립성 및 변경 제한

- 감사 thread는 기술 스펙을 작성한 현재 thread와 분리합니다.
- 감사 thread에는 작성자의 결론, 의도한 답, 예상 발견 사항을 전달하지 않습니다.
- 감사 thread는 제품 코드, 테스트, 설정, 기술 스펙을 수정하지 않습니다.
- 감사 thread가 쓸 수 있는 파일은 지정한 감사 보고서 하나뿐입니다.
- 블로커를 직접 해결하거나 스펙을 조용히 보정하지 않고 근거와 권고 수정안을 보고합니다.
- 감사 thread는 다른 구현 thread를 시작하거나 하위 작업으로 재인계하지 않습니다.

## 조사 범위

스펙의 모든 중요한 주장을 표본이 아니라 추적 가능한 단위로 대조합니다.

1. 승인된 PRD와 요구사항 추적표를 대조합니다.
2. 저장소의 실제 진입점, 모듈, 타입, 공개 API, 데이터 모델, 설정, 빌드·배포 경로와 테스트를 확인합니다.
3. 스펙에 적힌 파일 경로, 식별자, 명령어와 버전이 실제로 존재하거나 계획된 신규 항목으로 명확히 구분됐는지 확인합니다.
4. 상태 전이, ownership, threading, lifecycle, 오류 처리, 보안 경계, 호환성, migration과 rollback이 구현 가능한 계약인지 확인합니다.
5. 외부 API, SDK, 플랫폼 또는 프로토콜에 의존하는 주장은 해당 공식 문서나 저장소의 고정된 버전 자료를 대조합니다. 최신성에 민감한 정보는 반드시 현재 공식 자료로 검증합니다.
6. 테스트 스펙이 핵심 요구사항, 실패 모드와 블로커 해소를 검증할 수 있는지 확인합니다.
7. 구현 순서의 순환 의존성, 사용할 수 없는 도구·권한·자격 증명, 미정 데이터 마이그레이션과 배포 전제 조건을 찾습니다.

문서에 없는 새 제품 범위를 제안하는 일반 리뷰는 하지 않습니다. 각 발견은 구현 가능성이나 정확성에 직접 영향을 주어야 합니다.

## 발견 사항 분류

각 발견에 `AUD-001`부터 순번을 부여하고 다음 필드를 기록합니다.

| 필드 | 내용 |
|---|---|
| 심각도 | `블로커`, `중요`, `경미` |
| 유형 | `사실 불일치`, `구현 불가능`, `계약 누락`, `검증 공백`, `외부 의존성`, `요구사항 불일치` |
| 스펙 근거 | 섹션, 표, 계약 또는 라인 |
| 실제 근거 | 저장소 `path:line`, 실행 결과 또는 공식 자료 |
| 영향 | 그대로 구현할 때 실패하거나 달라지는 동작 |
| 권고 | 스펙 수정, 사용자 결정 또는 선행 작업 |

심각도는 다음 기준을 사용합니다.

- `블로커`: 현재 정보나 구조로 구현을 시작할 수 없거나, 시작하면 핵심 요구사항·데이터·보안·호환성을 위반합니다.
- `중요`: 구현은 가능하지만 스펙대로 하면 실제 시스템과 다르게 동작하거나 수용 기준을 신뢰할 수 없습니다.
- `경미`: 구현과 핵심 검증을 막지 않는 정합성 또는 명료성 문제입니다.

## 판정

감사 보고서의 판정은 하나만 사용합니다.

- `통과`: 블로커와 중요 발견이 없고 스펙이 구현·검증 기준으로 충분합니다.
- `조건부 통과`: 블로커는 없지만 구현 전에 스펙에 반영하거나 사용자가 명시적으로 수용해야 할 중요 발견이 있습니다.
- `차단`: 블로커가 하나 이상 있습니다.

`조건부 통과`의 중요 발견을 반영하지 않은 채 구현을 시작하지 않습니다. 사용자가 위험을 수용할 수 있는 항목은 그 결정과 영향이 기술 스펙에 기록된 뒤 새 SHA-256으로 다시 감사합니다.

## 감사 보고서 구조

```md
# 기술 스펙 감사 보고서: <대상>

**감사 판정:** 통과 | 조건부 통과 | 차단
**감사한 스펙:** <절대 경로>
**스펙 버전:** <버전>
**스펙 SHA-256:** <해시>
**저장소:** <절대 cwd>
**감사 시각:** <ISO 8601>

## 요약

## 구현 가능성

## 블로커

## 사실 불일치

## 계약 및 검증 공백

## 발견 사항

| ID | 심각도 | 유형 | 스펙 근거 | 실제 근거 | 영향 | 권고 |
|---|---|---|---|---|---|---|

## 확인한 근거

## 구현 전 필수 조치

## 감사 범위와 한계
```

발견이 없는 섹션에는 `없음`이라고 명시합니다. 실행하지 못한 검증과 접근하지 못한 외부 자료는 성공한 것처럼 쓰지 않고 `감사 범위와 한계`에 기록합니다.

## 모델과 추론 강도

사용자가 지정하지 않으면 기본값으로 `gpt-5.6-sol`과 `high`를 사용합니다. 감사 대상이 좁고 로컬 저장소만 대조하면 `gpt-5.6-terra`와 `medium`을 사용할 수 있습니다. 여러 플랫폼, 외부 계약, 보안·데이터·호환성 위험 또는 상충하는 자료가 있으면 `gpt-5.6-sol`과 `xhigh`를 사용합니다.

사용자가 모델이나 추론 강도를 지정하면 우선하되, 현재 새 작업 생성 도구가 해당 조합을 지원하지 않으면 가능한 조합을 알려 확인받습니다.

## 외부 감사 작업 생성

현재 호스트가 모델에 `thread/start`와 `turn/start`를 호출할 수 있는 도구 표면을 제공할 때만 새 감사 작업을 만듭니다.

1. 현재 기술 스펙 작업 이름과 새 감사 작업 이름을 같은 주제로 짓습니다.
2. 선택한 모델, 추론 강도와 감사 보고서 경로를 사용자에게 알립니다.
3. 기술 스펙 파일의 SHA-256을 계산합니다.
4. `thread/start`를 호출해 선택한 모델과 현재 프로젝트의 절대 `cwd`로 새 thread를 만듭니다.
5. 새 thread를 `<주제> 기술 스펙 감사`처럼 감사 목적이 드러나는 이름으로 바꿉니다.
6. 반환된 `threadId`로 `turn/start`를 호출하고 다음 입력 전체를 전달합니다.

```text
# 지시

## 목표

첨부한 기술 스펙을 실제 저장소, 승인된 요구사항과 필요한 공식 자료에 독립적으로 대조하여 구현 가능성, 블로커, 사실 불일치, 누락된 계약과 검증 공백을 조사하세요.

## 해야할것

- 기술 스펙 전체를 읽고 중요한 주장을 추적하세요.
- 저장소의 실제 코드, 설정, 빌드·배포 경로와 테스트를 근거 라인까지 확인하세요.
- 외부 계약에 의존하는 주장은 공식 자료로 확인하세요.
- 각 발견을 `AUD-*` ID, 심각도, 유형, 근거, 영향과 권고로 기록하세요.
- `통과`, `조건부 통과`, `차단` 중 하나로 판정하세요.
- 감사한 스펙의 SHA-256이 아래 값과 일치하는지 확인하세요.
- 지정한 경로에 한국어 감사 보고서를 작성하고 최종 응답에 링크를 첨부하세요.

## 하지 말아야할것

- 제품 코드, 테스트, 설정 또는 기술 스펙을 수정하지 마세요.
- 근거 없이 구현 가능하다고 추정하지 마세요.
- 문장 취향이나 새 제품 아이디어를 감사 발견으로 확대하지 마세요.
- 구현을 시작하거나 다른 작업으로 재인계하지 마세요.

## 판정 기준

- `통과`: 블로커와 중요 발견이 없음
- `조건부 통과`: 블로커는 없지만 반영 또는 명시적 수용이 필요한 중요 발견이 있음
- `차단`: 블로커가 하나 이상 있음

## 입력

- 저장소: <절대 cwd>
- 기술 스펙: <절대 경로>
- 스펙 버전: <버전>
- 스펙 SHA-256: <해시>
- 승인된 PRD: <절대 경로 또는 없음>
- 감사 보고서: <절대 경로>
```

새 thread와 첫 turn 생성에 성공하면 현재 작업에서는 감사를 중복 수행하거나 구현을 시작하지 않습니다.

## 실패 처리

- `thread/start` 또는 `turn/start`가 현재 모델의 도구로 노출되지 않았으면 현재 thread에서 감사를 대신 수행하지 않습니다.
- 선택한 모델, 추론 강도, 새 작업을 만들 수 없는 이유와 `turn/start`에 전달하려던 정확한 전체 프롬프트를 사용자에게 제공합니다.
- 보고서가 생성되지 않았거나 판정, 스펙 버전, SHA-256 중 하나가 없으면 감사가 완료된 것으로 보지 않습니다.
- 감사 thread가 보고서 외 파일을 변경했다면 해당 변경을 감사 결과로 신뢰하지 않고 사용자에게 알립니다.

## 구현 인계 조건

`start-implementation-thread`로 넘기기 전에 다음을 확인합니다.

- 감사 보고서의 스펙 경로, 버전과 SHA-256이 현재 기술 스펙과 일치합니다.
- 판정이 `통과`입니다.
- `블로커`와 `중요` 발견이 모두 해결됐고 해결 근거가 스펙에 반영됐습니다.
- 감사 이후 기술 스펙이 바뀌었다면 새 SHA-256으로 재감사했습니다.

하나라도 충족하지 못하면 구현 승인을 받아도 새 구현 thread를 만들지 않습니다.

## 동작 확인 시나리오

| 시나리오 | 기대 결과 |
|---|---|
| 기술 스펙 파일 작성 완료 | 별도 승인 없이 외부 감사 thread를 시작하고 현재 thread는 구현하지 않습니다. |
| 감사 판정이 `차단` | 블로커를 기술 스펙에 반영한 뒤 재감사합니다. |
| 감사 판정이 `조건부 통과` | 중요 발견을 반영하거나 위험 수용 결정을 스펙에 기록한 뒤 재감사합니다. |
| 감사 뒤 스펙 내용 변경 | 기존 보고서를 재사용하지 않고 새 SHA-256으로 재감사합니다. |
| 감사 판정이 `통과`이고 사용자가 별도 구현 승인 | `start-implementation-thread`의 나머지 게이트를 확인합니다. |
| 새 thread 도구가 없음 | 정확한 감사 프롬프트를 제공하고 구현 게이트를 미완료 상태로 둡니다. |
