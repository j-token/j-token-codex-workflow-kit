# Codex 실행 프롬프트 준비

## 출력 언어

사용자가 출력 언어를 명시적으로 지정하면 해당 언어를 사용합니다. 지정하지 않으면 이 스킬이 만드는 모든 사용자 대상 출력, 문서, 프롬프트, 보고서, 계획, 스펙 및 기타 산출물을 한국어로 작성합니다. 제목, 섹션, 레이블, 표, 체크리스트, 다이어그램과 템플릿에도 같은 언어를 사용합니다. 코드, 명령어, 파일 경로, 식별자, API 이름, 모델 ID, 프로토콜 이름과 필수 고유명사는 번역하지 않습니다.

## 목적

사용자가 설명해야 하는 양을 줄이되 LLM의 추정을 사실처럼 고정하지 않습니다. 조사 결과와 실행 계약을 한 파일에 모으고, 새 Codex 작업이 필요할 때 그대로 전달할 프롬프트까지 완성합니다.

## 첫 분류

요청을 다음 세 등급 중 하나로 분류합니다.

| 등급 | 기준 | 문서 | 승인 |
| --- | --- | --- | --- |
| `빠른 작업` | 범위와 완료 조건이 명확하고 국소적이며 실패 비용이 낮음 | 만들지 않음 | 사용자의 현재 실행 요청을 권한으로 보고 같은 작업에서 수행 |
| `계획 작업` | 여러 파일·시스템·조사·설계 판단이 필요하거나 별도 Codex 작업이 유리함 | 프롬프트 문서 1개 | 새 작업 생성 직전에 계획·모델·추론 강도·프롬프트를 한 번 확인 |
| `민감 작업` | 삭제, 배포, 외부 전송, 실제 결제 처리, 권한 변경, 비가역 데이터 변경, 보안·법적 고위험 | 프롬프트 문서 1개 | 위험 행동 직전에 대상과 영향을 명시적으로 승인받음 |

파일 수만으로 등급을 높이지 않습니다. 사용자가 이미 `수정해줘`, `구현해줘`, `실행해줘`라고 요청한 빠른 작업에는 문서 승인 메시지를 다시 요구하지 않습니다. 새 작업 생성은 사용자가 계획을 승인하며 새 작업 시작까지 명시한 경우에만 수행합니다.

## 조사 순서

1. 사용자의 의도를 1~3문장으로 재구성합니다. 내용이 충분하면 확인 답변을 기다리지 않고 조사합니다.
2. 지식 공백은 저장소의 코드·문서·이력·테스트에서 먼저 확인합니다.
3. 외부 사실, 최신 사양, 비교 대상 또는 사용자가 지정한 URL이 판단에 필요하면 브라우저로 공식·1차 자료를 조사합니다.
4. 남은 내용을 다음 상태로 분리합니다.
   - `확인된 사실`: 출처나 재현 방법이 있음
   - `추정`: 근거는 있지만 아직 검증되지 않음
   - `조건`: 사용자가 지켜야 한다고 한 범위·제약
   - `결정`: 채택한 선택과 사유
   - `열린 질문`: 답에 따라 실행 계약이 실제로 달라짐
5. 열린 질문 중 저장소나 자료로 해결할 수 있는 것은 묻지 않습니다. 되돌리기 쉬운 선택은 권장안을 문서에 밝히고 진행합니다.

## 문서 관리

`빠른 작업`에는 문서를 만들지 않습니다. `계획 작업`과 `민감 작업`에는 저장소 루트의 `.codex/prompts/`를 사용합니다.

```text
.codex/prompts/
├── README.md
├── active/<slug>.md
├── supporting/<slug>/<explicitly-requested-doc>.md
└── archive/YYYY/<slug>.md
```

- `README.md`는 전체 프롬프트 문서의 카탈로그입니다. 제목, 상태, 유형, 태그, 갱신일과 링크만 둡니다.
- `active/<slug>.md` 하나를 해당 작업의 권위 있는 프롬프트 문서로 사용합니다. PRD, 기술 스펙, 팩트 시트, 계획과 인계 프롬프트를 기본적으로 별도 파일로 쪼개지 않습니다.
- `supporting/`은 사용자가 별도 PRD·기술 스펙을 명시적으로 요청하거나 외부 고정 형식이 있을 때만 사용합니다. 실행 상태는 보조 문서에 중복하지 않습니다.
- 완료·취소·대체된 프롬프트 문서는 상태를 갱신한 뒤 `archive/YYYY/`로 옮기고 카탈로그 링크를 함께 갱신합니다.
- 장기간 여러 작업에서 재사용할 아키텍처 결정만 별도 ADR로 승격합니다. 조사 메모와 임시 JSON은 프롬프트 문서에 흡수한 뒤 남기지 않습니다.
- 사용자가 별도 PRD·기술 스펙을 명시적으로 요구하거나 외부 조직의 고정 형식이 필요한 경우에만 `supporting/<slug>/`에 보조 문서를 만들고 프롬프트 문서에서 연결합니다.

실행 계약은 작업당 프롬프트 문서 1개입니다. 저장소에 카탈로그가 처음 없다면 최초 프롬프트 생성 시 `.codex/prompts/README.md`와 프롬프트 문서로 실제 파일 2개를 만들고, 이후에는 프롬프트 문서 1개를 추가하며 카탈로그 1개를 갱신합니다.

처음 `.codex/prompts/README.md`를 만들 때는 다음 열만 사용합니다.

```md
# Codex 프롬프트 카탈로그

| 프롬프트 | 상태 | 유형 | 태그 | 갱신일 |
| --- | --- | --- | --- | --- |
```

```text

```

<!-- codex-workflow:prompt:end -->

## 결과와 후속
```

frontmatter의 허용 값은 다음과 같습니다.

- `status`: `draft`, `ready`, `running`, `done`, `cancelled`, `superseded`
- `type`: `plan`, `bug`, `ui`, `mixed`
- `risk`: `quick`, `standard`, `sensitive`
- `reasoning_effort`: 새 작업 도구 또는 현재 호스트 모델 카탈로그가 지원하는 값

`risk: sensitive`는 프롬프트 문서 전체에 추가 승인을 반복하라는 뜻이 아닙니다. 코드·테스트 작성은 계획 승인으로 수행하고, 실제 운영 배포·결제 트래픽 전환·권한 부여·비가역 데이터 변경처럼 문서에 열거한 위험 행동 직전에만 대상을 다시 확인합니다.

## 실행 계획 규칙

- 계획은 파일 개수가 아니라 사용자가 확인할 수 있는 결과 단위로 나눕니다.
- 각 단계는 `변경 → 검증`을 한 블록에 둡니다.
- 팩트 ID나 조건을 계획 단계와 검증에 연결합니다.
- 사용자가 말하지 않은 기능을 편의를 이유로 범위에 넣지 않습니다.
- 기각한 대안은 실제로 검토한 것만 한 줄 사유와 함께 남깁니다.

## 모델과 추론 강도

현재 새 작업 도구의 스키마에서 사용 가능한 모델과 강도를 먼저 확인합니다. 새 작업 도구가 아직 없으면 현재 호스트가 제공한 모델 카탈로그나 공식 제품 문서에서 확인합니다. 둘 다 없으면 모델 ID를 만들지 말고 `미확정 — 새 작업 UI에서 지원 모델 선택 필요`라고 기록합니다. 사용자가 지정하지 않았으면 필요한 결과를 낼 수 있는 가장 가벼운 확인 가능한 조합을 권장합니다.

- 빠르고 국소적인 작업: 사용 가능한 빠른 모델 + `low`
- 일반 다중 파일 구현·조사: 균형 모델 + `medium`
- 아키텍처·보안·데이터·호환성 고위험: 가장 강한 모델 + `high` 이상

모델 ID를 기억으로 만들지 않습니다. 선택 사유에는 파일 수가 아니라 남은 판단 수, 시스템 상호작용, 검증 난이도와 실패 비용을 적습니다. 사용자가 모델이나 추론 강도를 수정하면 지원 여부만 확인하고 그 선택을 우선합니다. 프롬프트 문서의 `reasoning_effort`는 Codex Desktop 새 작업 도구의 `thinking` 인자로 같은 값 그대로 매핑합니다.

## 프롬프트 계약

새 작업용 프롬프트에는 다음을 모두 넣습니다.

1. 완료 목표
2. 해야 할 일과 하지 말아야 할 일
3. 확인된 사실·조건·사용자 결정
4. 먼저 읽을 파일과 외부 근거
5. 단계별 검증과 완료 보고 형식
6. 문서 열람만 하고 다시 인계하지 말고 구현·검증까지 끝내라는 지시
7. 원래 사용자 요청

대화 맥락을 그대로 덤프하지 말고 실행에 필요한 의미를 앞의 항목에 구조화합니다. 원래 요청은 마지막에 보존합니다.

## 승인과 실행

프롬프트 문서를 완성하면 다음 명령을 foreground로 실행하고 사용자가 브라우저 검토를 끝낼 때까지 기다립니다.

```text
codex-workflow review .codex/prompts/active/<slug>.md --json
```

- 프로세스가 조용해도 사용자가 읽거나 수정하는 중일 수 있으므로 임의로 종료·재시작·중복 실행하지 않습니다.
- 브라우저 화면은 조사·계획 문서, 모델, 추론 강도와 새 작업용 프롬프트를 한 번에 보여줍니다.
- `approved` 결과의 `model`, `reasoningEffort`, `prompt`를 프롬프트 문서의 frontmatter와 `Codex 실행 프롬프트` 본문에 정확히 반영하고 `status: ready`로 바꿉니다.
- `cancelled`이면 새 Codex 작업을 만들지 않고 검토가 취소됐다고 알립니다.

바이너리 출력 계약은 다음과 같습니다.

```json
{
  "status": "approved",
  "path": "<절대 프롬프트 문서 경로>",
  "model": "<사용자 선택 모델>",
  "reasoningEffort": "<사용자 선택 추론 강도>",
  "prompt": "<사용자가 승인한 완전한 프롬프트>"
}
```

`codex-workflow` 명령을 찾을 수 없으면 설치를 자동 실행하지 말고 사용자의 운영체제에 맞는 명령을 안내합니다.

macOS와 Linux:

```sh
curl -fsSL https://raw.githubusercontent.com/j-token/j-token-codex-workflow-kit/main/scripts/install.sh | sh
```

Windows PowerShell:

```powershell
irm https://raw.githubusercontent.com/j-token/j-token-codex-workflow-kit/main/scripts/install.ps1 | iex
```

사용자가 설치하지 않기로 하거나 설치가 실패하면 작업을 차단하지 않고 채팅에서 같은 세 항목을 검토하는 fallback을 사용합니다.

사용자가 한 번에 검토할 항목은 다음 세 가지입니다.

- 실행 계획
- 모델과 추론 강도
- 새 작업에 전달할 프롬프트

바이너리 결과가 `approved`이거나 채팅 fallback에서 사용자가 `이 계획으로 새 작업 시작`, `승인하고 새 작업 생성`처럼 새 작업 생성을 명시하면 `start-implementation-thread`를 적용합니다. 사용자가 모델이나 강도를 바꾸면 프롬프트 문서의 메타데이터와 `Codex 실행 프롬프트` 본문을 함께 갱신한 뒤 실행합니다. 단순한 `좋아`를 외부·비가역 행동의 승인으로 확대 해석하지 않습니다.

## 완료 점검

- [ ] 빠른 작업에 불필요한 문서를 만들지 않았는가
- [ ] 계획 작업의 실행 진실이 프롬프트 문서 하나에 모였는가
- [ ] 사실·추정·조건·결정·열린 질문이 구분됐는가
- [ ] 각 사실에 근거 또는 확인 방법이 있는가
- [ ] 모델·추론 강도·사유와 수정 가능성이 적혀 있는가
- [ ] 새 작업용 프롬프트가 독립 실행 가능한가
- [ ] 바이너리 승인 결과 또는 채팅 fallback을 프롬프트 문서에 반영했는가
- [ ] 승인 횟수가 위험과 새 작업 생성에 필요한 최소 횟수인가

## 문서 관리 근거

사용자가 단일 프롬프트 문서, 카탈로그, 패싯, 보조 문서 승격 기준이나 Plannotator와의 차이를 물으면 [Codex 프롬프트 문서 관리 조사](../../references/prompt-document-management.md)를 읽고 근거를 설명합니다. 일반 프롬프트 작성에는 이 참조를 매번 불러오지 않습니다.
